CHAPTER 00

全体像 — Webページが開くまで

手を動かす前に、これから作るものの全体像を掴みます。ブラウザに https://example.com と打ってからページが表示されるまで、裏では次のことが起きています。

  1. 名前解決 — ブラウザは Route 53 に「example.com のIPアドレスは？」と聞き、ALBの住所を得る
  2. HTTPS接続 — Internet Gateway を通ってALBへ。ALBが証明書(ACM)を使って暗号化通信を受け付ける
  3. 画面 & API — ALBがNext.jsコンテナ(ポート3000)に転送。ページ表示も、ページ内のJSが叩く /api/... も、同じコンテナのRoute Handlerが処理する
  4. データ取得 — Route HandlerがRDS(PostgreSQL)にSQLを投げ、結果をJSONで返す

登場するサービスと役割

VPC
AWS内に作る自分専用のネットワーク。全ての土台
ECS on Fargate
コンテナをサーバー管理なしで動かす実行基盤
ECR
Dockerイメージの保管庫。ECSはここから取得する
ALB
リクエストの玄関。HTTPSを終端し、複数タスクに負荷分散
RDS
マネージドDB。バックアップやパッチをAWSが面倒見る
パラメータストア
DBパスワード等の秘密情報の金庫。コードに書かない
Route 53
DNS。ドメイン名とALBを結びつける住所録
ACM
HTTPS用のサーバー証明書を無料で発行・自動更新

CHAPTER 02

VPC — ネットワークの土台

VPCは「AWS内に借りる自分専用の区画」。この中をインターネットから届く区画（パブリック）と届かない区画（プライベート）に分け、ALBは表に、アプリとDBは奥に置きます。

VPC 10.0.0.0/16（今回作るもの）
パブリックサブネット ×2 (AZ-a / AZ-b)
ALB と NAT Gateway を配置。インターネットゲートウェイ経由で外と直接通信できる。
プライベートサブネット ×2 (AZ-a / AZ-b)
ECSタスクとRDSを配置。外から直接届かない。外向き通信はNAT経由のみ。
🎯
VPCというサービスの目的 — 誰がどこに入れるかをネットワークの層で制御するため。アプリやDBを直接インターネットに晒さない構成が、すべてのAWS設計の基本形です。

手順 — 「VPCなど」ウィザードで一括作成

1
VPC コンソール›VPCを作成
作成するリソースで「VPCなど」を選択（VPC単体ではなく、サブネット・ルートテーブルまで一括で作れるウィザード）。名前タグに handson。
2
下記のとおり設定します。
IPv4 CIDR10.0.0.0/16（既定のまま） AZ数2 パブリックサブネット2 プライベートサブネット2 NATゲートウェイ1AZ内（学習用。本番は「AZごと」） VPCエンドポイントなし
3
右側の「プレビュー」で構成図を確認して「VPCを作成」。1〜2分で完了します。
✅
実行するとこうなる — VPC詳細の「リソースマップ」に、サブネット4つ・ルートテーブル・インターネットゲートウェイ・NATゲートウェイが線で結ばれて表示されます。この図が2章の内容そのものです。
⚠️
課金注意 — NAT Gateway はこの瞬間から時間課金（約$0.045/時+通信量）が始まります。数日空ける場合は11章を参考に一旦削除を。

CHAPTER 03

セキュリティグループ設計

セキュリティグループ(SG)はリソースごとの防火扉。「どこから・どのポートに入ってよいか」を決めます。今回は3枚の扉を鎖のようにつなぎます。

alb-sg
443/80 を
全世界(0.0.0.0/0)から許可
→
app-sg
3000 を
alb-sgから来た通信のみ許可
→
db-sg
5432 を
app-sgから来た通信のみ許可
🎯
この設計の目的 — SGのソース(送信元)にIPアドレスではなく別のSGを指定できるのがポイント。「ALBを通った通信だけがアプリに届き、アプリを通った通信だけがDBに届く」一方通行の鎖を作ります。

手順 — 3つのSGを順に作成

1
VPC コンソール›セキュリティグループ›セキュリティグループを作成
名前 alb-sg、VPCは2章で作った handson-vpc を選択。インバウンドルールに HTTPS(443)・HTTP(80)、ソース 0.0.0.0/0 を追加して作成。
2
同様に app-sg を作成。インバウンドは カスタムTCP 3000 の1行、ソースは「カスタム」で検索欄に alb-sg と入れてSGを選択。
3
db-sg を作成。インバウンドは PostgreSQL(5432) 1行、ソースに app-sg を指定。
✅
実行するとこうなる — 3つのSGが一覧に並びます。db-sg のインバウンドを開くと、ソース欄に app-sg のID(sg-xxxx)が入っているはず。これが「SG参照」です。

CHAPTER 04

RDS — PostgreSQL を立てる

DBサーバーを自分でインストール・運用する代わりに、AWSのマネージドDB「RDS」を使います。プライベートサブネットに置き、外からは一切届かない構成にします。

🎯
RDSというサービスの目的 — バックアップ・パッチ適用・障害時の復旧をAWSに任せられるDB。EC2に自分でPostgreSQLを入れる運用と比べ、手間と事故リスクが大幅に減ります。

手順 — DBインスタンス作成

1
RDS コンソール›データベースの作成
「標準作成」→ エンジン「PostgreSQL」を選択。テンプレートは「無料利用枠」（なければ「開発/テスト」）。
2
主な設定値：
DB識別子handson-db マスターユーザーappuser／パスワードは「自己管理」で強いものを生成し控える インスタンスdb.t4g.micro VPChandson-vpc パブリックアクセスなし（重要。外から直接つながせない） セキュリティグループ既存の db-sg を選択（defaultは外す） 最初のDB名「追加設定」を開いて appdb と入力
3
「データベースの作成」をクリック。ステータスが「作成中」→「利用可能」になるまで5〜10分待つ。完了したらDB詳細画面の「接続とセキュリティ」からエンドポイント（xxx.rds.amazonaws.com）をコピーして控える。
✅
実行するとこうなる — DBは起動しますが、パブリックアクセスなし＋db-sgの制限により、現時点ではどこからも接続できません。8章でECSタスク(app-sg)が動き始めて、初めて接続できるようになります。

CHAPTER 05

パラメータストアで秘密情報管理

DBのパスワードをコードや設定ファイルに直書きしないのが実務の鉄則。Systems Manager の「パラメータストア」に保存し、8章でECSタスクに環境変数として注入します。

🎯
パラメータストアの目的 — 秘密情報の保管と配布を一元化するため。コードに書くとGitに残り漏洩します。無料で使え、暗号化(SecureString)もできます。ローテーション自動化まで必要になったら有償のSecrets Managerへ。

手順 — 接続情報を4つ保存

1
Systems Manager コンソール›パラメータストア›パラメータの作成
次の4つを1つずつ作成します（名前は階層で整理するのが定石）。
/handson/db/hostString4章で控えたRDSエンドポイント /handson/db/nameStringappdb /handson/db/userStringappuser /handson/db/passwordSecureStringDBパスワード（暗号化して保存）
2
パスワードだけはタイプで「SecureString」を選ぶこと（KMSで暗号化される）。他はStringでOK。
✅
実行するとこうなる — 一覧に4つのパラメータが並び、passwordのタイプ欄だけ「SecureString」と表示されます。値は画面上でマスクされます。

CHAPTER 06

アプリを Docker 化する

ECSで動かせる形＝コンテナイメージにします。この章だけはAWSでなく手元のPCでの作業。Next.js（画面）にAPIもRoute Handlersとして同居させ、1つの Dockerfile を書き、ローカルで動くことを確認してから次へ進みます。

API 部分 — Route Handlers（最小構成）

Next.js の App Router では app/api/.../route.ts を置くだけで、同じコンテナがAPIエンドポイントになります。別のAPIサーバーは不要。

app/api/health/route.ts
export function GET() {
  return Response.json({ status: "ok" });
}
app/api/messages/route.ts
import { Pool } from "pg";

// 毎リクエスト実行（ビルド時の静的化を防ぐ）
export const dynamic = "force-dynamic";

// 環境変数から接続情報を組み立てる（8章でECSが注入する）
const pool = new Pool({
  host: process.env.DB_HOST,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  port: 5432,
});

export async function GET() {
  await pool.query(
    "CREATE TABLE IF NOT EXISTS messages (id serial, body text)");
  const { rows } = await pool.query(
    "SELECT id, body FROM messages ORDER BY id");
  return Response.json(rows);
}

依存は npm install pg（TypeScriptなら npm install -D @types/pg も）の追加だけ。

Dockerfile

ポイントは2つ。① next.config.js に output: "standalone" を指定してイメージを軽くする。② ページ内のAPI呼び出しは fetch("/api/messages") のように同一ドメインの相対パスで書く（同じコンテナのRoute Handlerが応えるので、APIのURLを埋め込む必要がない）。

Dockerfile（マルチステージ）
FROM node:22-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-slim
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/.next/standalone ./
COPY --from=build /app/.next/static ./.next/static
COPY --from=build /app/public ./public
EXPOSE 3000
CMD ["node", "server.js"]

ローカルで通し確認（docker compose）

compose.yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: localpass
      POSTGRES_DB: appdb
  app:
    build: .
    environment:
      DB_HOST: db
      DB_USER: appuser
      DB_PASSWORD: localpass
      DB_NAME: appdb
    ports: ["3000:3000"]
bash — 動作確認
docker compose up --build

# 別ターミナルで
curl http://localhost:3000/api/health
# => {"status":"ok"}
# ブラウザで http://localhost:3000 を開きページ表示を確認
✅
実行するとこうなる — ローカルの2コンテナ（app / db）が起動し、ブラウザでページが表示されます。この「動く状態」を、7章以降でそのままAWSに持っていきます。

CHAPTER 07

ECR — イメージ置き場

手元でビルドしたイメージをAWSに置きます。ECSは実行時にここからイメージを取得します。

🎯
ECRの目的 — Docker Hubと同じ「コンテナレジストリ」のAWS版。同一リージョン内のECSからの取得が速く、IAMで取得権限を制御できます。

手順

1
ECR コンソール›リポジトリを作成
「プライベート」で handson-app を1つ作成。
2
リポジトリを開き「プッシュコマンドを表示」の内容を実行（下記はまとめたもの。ACCOUNT_IDは自分の12桁に置き換え）。
bash — ビルド&プッシュ
ACCOUNT_ID=123456789012
REGISTRY=$ACCOUNT_ID.dkr.ecr.ap-northeast-1.amazonaws.com

aws ecr get-login-password --region ap-northeast-1 | \
  docker login --username AWS --password-stdin $REGISTRY

# Fargate(x86_64)向けにビルドする点に注意（Apple Silicon の人は必須）
docker build --platform linux/amd64 -t $REGISTRY/handson-app:v1 .
docker push $REGISTRY/handson-app:v1
✅
実行するとこうなる — リポジトリの「イメージ」タブに v1 タグのイメージが表示されます。このURI（...amazonaws.com/handson-app:v1）を8章で使うので控えておく。
⚠️
Apple Siliconの罠 — M1/M2/M3 Macで --platform linux/amd64 を付け忘れると、ECSタスクが「exec format error」で即死します。原因に気づきにくい定番トラブル。

CHAPTER 08

ECS — クラスターとタスク定義

ECSの登場人物は3つ。クラスター（入れ物）、タスク定義（コンテナの設計図）、サービス（設計図どおりに常時N個動かし続ける仕組み・9章で作成）。Fargateを選ぶと、下で動くサーバーの管理が不要になります。

手順 1 — クラスター作成

1
ECS コンソール›クラスター›クラスターの作成
名前 handson-cluster、インフラは「AWS Fargate」のみチェックで作成。

手順 2 — タスク定義

🎯
2つのロールの違い — タスク実行ロール＝ECS自身がタスクを起動するための権限（ECRからのpull、パラメータストアの読み取り、ログ書き込み）。タスクロール＝アプリのコードがAWSを呼ぶ時の権限（今回は不要）。混同しやすいので注意。
1
ECS コンソール›タスク定義›新しいタスク定義の作成
ファミリー名 handson-app、起動タイプ Fargate、CPU 0.25 vCPU / メモリ 0.5 GB。タスク実行ロールは「新しいロールの作成」。
2
コンテナ設定：名前 app、イメージURIは7章で控えた .../handson-app:v1、コンテナポート 3000。
3
「環境変数」セクションで、5章のパラメータを「ValueFrom」として注入：
DB_HOSTValueFrom/handson/db/host DB_NAMEValueFrom/handson/db/name DB_USERValueFrom/handson/db/user DB_PASSWORDValueFrom/handson/db/password
これで6章のコードの process.env.DB_* に、起動時に値が入ります。コードに秘密が書かれない仕組みの完成。
📌
初回は「実行ロールにSSM読み取り権限がない」エラーでタスクが落ちることがあります。その場合はIAMコンソールで ecsTaskExecutionRole にインラインポリシーで ssm:GetParameters（対象 /handson/* ）を追加してください（2章のLambda資料・実行ロール追加と同じ手順です）。
✅
実行するとこうなる — タスク定義が1つ登録されます。まだコンテナは動いていません（設計図を書いただけ）。動かすのは9章の「サービス」です。

CHAPTER 09

ALB & サービス起動

いよいよ動かします。ALB（玄関）を立て、画面も /api/* も同じNext.jsコンテナへ転送する設定を行い、ECSサービスでコンテナを常駐させます。

手順 1 — ターゲットグループを作成

1
EC2 コンソール›ターゲットグループ›ターゲットグループの作成
タイプは「IPアドレス」(Fargateはこれ)。名前 app-tg、プロトコルHTTP:3000、VPCは handson-vpc、ヘルスチェックパス /api/health。ターゲットは登録せず作成（サービスが自動登録する）。

手順 2 — ALB作成

1
EC2 コンソール›ロードバランサー›Application Load Balancer を作成
名前 handson-alb、「インターネット向け」、VPCは handson-vpc、マッピングでパブリックサブネット2つを選択、SGは alb-sg。リスナー HTTP:80 の転送先に app-tg を指定して作成。画面も /api/* も同じコンテナが処理するため、パスルーティングのルール追加は不要。

手順 3 — ECSサービスを起動

1
handson-cluster›サービス›作成
タスク定義 handson-app、サービス名 app-svc、必要なタスク数 1。ネットワーキング：プライベートサブネット2つ・SGは app-sg・パブリックIPはオフ。ロードバランシングでALB → リスナー80:HTTP → app-tg を選択して作成。

動作確認

bash — ALBのDNS名で確認
# ALB詳細画面の「DNS名」をコピーして
curl http://handson-alb-xxxx.ap-northeast-1.elb.amazonaws.com/api/health
# => {"status":"ok"}

# ブラウザで同じDNS名を開くと Next.js のページが表示される
✅
実行するとこうなる — ここが本ハンズオン最大の山場です。ブラウザにページが出れば、①〜④の流れ（ALB→Next.js(Route Handlers)→RDS）がすべて貫通しています。エラーの場合はサービスの「イベント」タブとタスクの「ログ」タブを見るのが定石（11章）。

CHAPTER 10

Route 53 & HTTPS 化

仕上げです。ALBの長いDNS名を自分のドメインに置き換え、ACMの証明書でHTTPSにします。ドメイン代（.comで年約$14〜）だけは実費がかかります。

手順 1 — ドメイン取得

1
Route 53 コンソール›登録済みドメイン›ドメインの登録
好きなドメイン名を検索して購入（連絡先情報の入力が必要。登録完了まで最大数十分）。既にお名前.com等で持っている場合はそのドメインのNSをRoute 53のホストゾーンに向ければ同じことができます。
2
登録が完了すると「ホストゾーン」に自分のドメインが自動作成されている。これがこのドメインの住所録本体。

手順 2 — ACMで証明書を発行

🎯
ACMの目的 — HTTPSに必要なサーバー証明書を無料で発行し、期限前の更新も自動でやってくれるサービス。ALBとセットで使うのが定番。
1
Certificate Manager コンソール›証明書をリクエスト
「パブリック証明書」、ドメイン名に取得したドメイン（例 example.com）、検証方法「DNS検証」でリクエスト。
2
証明書詳細画面の「Route 53 でレコードを作成」ボタンを押す（検証用のCNAMEが自動で追加される）。数分でステータスが「発行済み」になる。

手順 3 — HTTPSリスナーとAレコード

1
handson-alb›リスナー›リスナーの追加
HTTPS:443、証明書に手順2のものを選択、デフォルトアクションは app-tg へ転送。
2

CHAPTER 11

運用の基本と片付け

「動いた後」に毎日使う3つの操作と、課金を止める削除手順です。

日常の3操作

ログを見る
クラスター › サービス › タスク › 「ログ」タブ。コンテナの標準出力がそのままCloudWatch Logsに流れています。エラー調査はまずここ。
新バージョンを出す
7章の手順で :v2 をpush → タスク定義の「新しいリビジョンの作成」でタグを差し替え → サービスの「更新」で新リビジョンを選択。旧タスクと入れ替わるローリング更新が走ります。
増やす/減らす
サービスの「必要なタスク数」を変えるだけで台数が増減。さらに「Auto Scaling」でCPU使用率に応じた自動増減も設定できます。

片付け（課金を止める順番）

⚠️
削除は依存の逆順で — 使っている物が残っていると削除に失敗します。上から順に消してください。
  1. ECSサービス（タスク数を0に更新 → 削除）→ クラスター削除
  2. ALB削除 → ターゲットグループ削除
  3. RDSインスタンス削除（最終スナップショット不要にチェック）
  4. NAT Gateway削除 → 解放されたElastic IPも解放
  5. VPC削除（サブネット等も一括で消える）
  6. ECRリポジトリ削除（イメージごと）
  7. パラメータストアの4つ、CloudWatchロググループを削除
  8. Route 53：Aレコード削除。ドメイン自体は年額課金なので更新設定を確認（自動更新オフに）
✅
最後の確認 — 翌日以降に Billing コンソールの「コスト詳細」を開き、課金が止まっていることを確認したら完了です。おつかれさまでした。
