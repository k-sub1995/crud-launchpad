CHAPTER 00

全体像 — Webページが開くまで

手を動かす前に、これから作るものの全体像を掴みます。
ブラウザに https://example.com と打ってからページが表示されるまで、
裏では次のことが起きています。

  1. 名前解決 — ブラウザは Route 53 に「example.com のIPアドレスは？」と聞き、
    ALBの住所を得る
  2. HTTPS接続 — Internet Gateway を通ってALBへ。
    ALBが証明書(ACM)を使って暗号化通信を受け付ける
  3. 画面 & API — ALBがNext.jsコンテナ(ポート3000)に転送。
    ページ表示も、ページ内のJSが叩く /api/... も、
    同じコンテナのRoute Handlerが処理する
  4. データ取得 — Route HandlerがRDS(PostgreSQL)にSQLを投げ、
    結果をJSONで返す

登場するサービスと役割

VPC
AWS内に作る自分専用のネットワーク。全ての土台
ECS on Fargate
コンテナをサーバー管理なしで動かす実行基盤
ECR
Dockerイメージの保管庫。ECSはここから取得する
ALB
リクエストの玄関。HTTPSを終端し、複数タスクに負荷分散
RDS
マネージドDB。バックアップやパッチをAWSが面倒見る
パラメータストア
DBパスワード等の秘密情報の金庫。コードに書かない
Route 53
DNS。ドメイン名とALBを結びつける住所録
ACM
HTTPS用のサーバー証明書を無料で発行・自動更新

CHAPTER 02

VPC — ネットワークの土台

VPCは「AWS内に借りる自分専用の区画」。
この中をインターネットから届く区画（パブリック）と届かない区画（プライベート）に分けます。

VPC 10.0.0.0/16（今回作るもの）
パブリックサブネット ×2 (AZ-a / AZ-b)
ALB と NAT Gateway を配置。
インターネットゲートウェイ経由で外と直接通信できる。
プライベートサブネット ×2 (AZ-a / AZ-b)
ECSタスクとRDSを配置。
外から直接届かない。
外向き通信は基本NAT経由（S3宛てのみS3ゲートウェイエンドポイント経由）。
🎯
VPCというサービスの目的 — 誰がどこに入れるかをネットワークの層で制御するため。
アプリやDBを直接インターネットに晒さない構成が、すべてのAWS設計の基本形です。

名前タグに handson。
2
下記の通り設定します（画像参照）。
IPv4 CIDR10.0.0.0/16（既定） AZの数2（既定） パブリックサブネットの数2（既定） プライベートサブネットの数2（既定） NATゲートウェイリージョナル - 新規 VPCエンドポイントS3ゲートウェイ
3

CHAPTER 03

セキュリティグループ設計

セキュリティグループ(SG)はリソースごとの防火扉。
「どこから・どのポートに入ってよいか」を決めます。
今回は3枚の扉を鎖のようにつなぎます。

alb-sg
443/80 を
全世界(0.0.0.0/0)から許可
→
app-sg
3000 を
alb-sgから来た通信のみ許可
→
db-sg
5432 を
app-sgから来た通信のみ許可
🎯
この設計の目的 — SGのソース(送信元)にIPアドレスではなく別のSGを指定できるのがポイント。
「ALBを通った通信だけがアプリに届き、アプリを通った通信だけがDBに届く」一方通行の鎖を作ります。

手順 — 3つのSGを順に作成

1
VPC コンソール›セキュリティグループ›セキュリティグループを作成
名前 alb-sg、VPCは2章で作った handson-vpc を選択。
インバウンドルールに HTTPS(443)・HTTP(80)、ソース Anywhere-IPv4(0.0.0.0/0) を追加して作成。
2
同様に app-sg を作成。
インバウンドは カスタムTCP 3000 、ソースは「カスタム」で検索欄に alb-sg と入れてSGを選択して作成。
3
db-sg を作成。
インバウンドは PostgreSQL(5432) 、ソースに app-sg と入れてSGを選択して作成。
✅
実行するとこうなる — 3つのSGが一覧に並びます。
例としてdb-sg を選択しインバウンドルールを開くと、ソース欄に app-sg のID(sg-xxxx)が入っています。
これが「SG参照」——ソースをIPアドレスではなく別のSGで指定する仕組みで、app-sgが付いたリソース（ECSタスク）からの通信だけを通します。ALBやECSのIPが変わっても設定を直す必要がありません。

RDS — PostgreSQL を立てる

DBサーバーを自分でインストール・運用する代わりに、AWSのマネージドDB「RDS」を使います。
プライベートサブネットに置き、外からは一切届かない構成にします。

🎯
RDSというサービスの目的 — バックアップ・パッチ適用・障害時の復旧をAWSに任せられるDB。
EC2に自分でPostgreSQLを入れる運用と比べ、手間と事故リスクが大幅に減ります。

CHAPTER 07

ECS — クラスターとタスク定義

ECSの登場人物は3つ。
・クラスター（入れ物）
・タスク定義（コンテナの設計図）
・サービス（設計図どおりに常時N個動かし続ける仕組み・8章で作成）
Fargateを選ぶと、下で動くサーバーの管理が不要になります。

💡 TIPS — ECS on EC2 と on Fargate、何が違う？
ECS on EC2
📦 コンテナ（アプリ）
🖥 OS・ミドルウェア（パッチ適用）
🏗 EC2インスタンス（台数・スケール）
🟧 = あなたが管理（3層ぜんぶ）
ECS on Fargate ← 今回はこっち
📦 コンテナ（アプリ）
🖥 OS・ミドルウェア
🏗 サーバー（見えない・意識しない）
🟦 = AWSにおまかせ（管理はコンテナだけ）
結論: デファクトは Fargate
 サーバー管理ゼロ・課金はタスクが使った vCPU・メモリ分だけでスケールも自動。
EC2を選ぶのは「GPUが必要」「特殊なインスタンスタイプを使いたい」など明確な理由があるときだけ。

CHAPTER 09

Route 53 & HTTPS 化

仕上げです。
ALBの長いDNS名を自分のドメインに置き換え、ACMの証明書でHTTPSにします。
ドメイン代（.comで年約$14〜）だけは実費がかかります。

手順 1 — ドメイン取得

1
Route 53 コンソール›登録済みドメイン›ドメインの登録
好きなドメイン名を検索して購入（連絡先情報の入力が必要。登録完了まで最大数十分）。
既にお名前.com等で持っている場合はそのドメインのNSをRoute 53のホストゾーンに向ければ同じことができます。
2
登録が完了すると「ホストゾーン」に自分のドメインが自動作成されている。
これがこのドメインの住所録本体。

手順 2 — ACMで証明書を発行

🎯
ACMの目的 — HTTPSに必要なサーバー証明書を無料で発行し、期限前の更新も自動でやってくれるサービス。
ALBとセットで使うのが定番。
1
Certificate Manager コンソール›証明書をリクエスト
「パブリック証明書」、ドメイン名に取得したドメイン（例 example.com）、検証方法「DNS検証」でリクエスト。
2
証明書詳細画面の「Route 53 でレコードを作成」ボタンを押す（検証用のCNAMEが自動で追加される）。
数分でステータスが「発行済み」になる。

手順 3 — HTTPSリスナーとAレコード

1
handson-alb›リスナー›リスナーの追加
HTTPS:443、証明書に手順2のものを選択、デフォルトアクションは app-tg へ転送。
2
既存の HTTP:80 リスナーを編集し、アクションを「HTTPS 443 へリダイレクト」に変更（httpで来た人を自動でhttpsへ）。
3
Route 53›ホストゾーン›レコードを作成
レコードタイプ A、「エイリアス」をON → 「Application Load Balancer へのエイリアス」→ ap-northeast-1 → handson-alb を選択して作成。
✅
実行するとこうなる — https://自分のドメイン でページが開き、アドレスバーに鍵マークが付きます。
http で開いても自動で https に転送されます。
これで0章の図の全要素が完成です。

CHAPTER 10

運用の基本と片付け

「動いた後」に毎日使う3つの操作と、課金を止める削除手順です。

日常の3操作

ログを見る
クラスター › サービス › タスク › 「ログ」タブ。
コンテナの標準出力がそのままCloudWatch Logsに流れています。
エラー調査はまずここ。
新バージョンを出す
6章の手順で :v2 をpush → タスク定義の「新しいリビジョンの作成」でタグを差し替え → サービスの「更新」で新リビジョンを選択。
旧タスクと入れ替わるローリング更新が走ります。
増やす/減らす
サービスの「必要なタスク数」を変えるだけで台数が増減。
さらに「Auto Scaling」でCPU使用率に応じた自動増減も設定できます。

片付け（課金を止める順番）

⚠️
削除は依存の逆順で — 使っている物が残っていると削除に失敗します。
上から順に消してください。
  1. ECSサービス（タスク数を0に更新 → 削除）→ クラスター削除
  2. ALB削除 → ターゲットグループ削除
  3. RDSインスタンス削除（最終スナップショット不要にチェック）
  4. NAT Gateway削除 → 解放されたElastic IPも解放
  5. VPC削除（サブネット等も一括で消える）
  6. ECRリポジトリ削除（イメージごと）
  7. パラメータストアの4つ、CloudWatchロググループを削除
  8. Route 53：Aレコード削除。ドメイン自体は年額課金なので更新設定を確認（自動更新オフに）
✅
最後の確認 — 翌日以降に Billing コンソールの「コスト詳細」を開き、課金が止まっていることを確認したら完了です。
おつかれさまでした。
