献立アプリで学ぶ Next.js 入門

React → Next.js 置き換えマップ

React版レシピアプリ（react-learning/ — viewModeで3画面切替・localStorage保存）の実コードを題材に、Next.jsの主要概念を比較して学びます。

ページが表示されるまでの流れ — いちばん大事な違い
React（今: CSR） ほぼ空のHTMLが届く → JSをダウンロード → ブラウザでReactが実行 → やっと画面が出る
Next.js（SSR） サーバーでReactを実行 → 完成済みHTMLが届く（即表示） → 後からJSが動き出す（ハイドレーション）

Next.js = 「Reactをどこで・いつ実行するか」を選べるようにしたフレームワーク。

コンポーネント・state・propsなどReactの知識はすべてそのまま使います。

新しく増えるのは「サーバーで動く部分」と「その境界線の引き方」です。

01

そもそもReactとは？ Next.jsとは？

この先ずっと「CSR」「SSR」のようなレンダリング方式の話が続きますが、その前に一番土台になる認識をそろえます。

ReactとNext.jsは対立する2つの技術ではなく、Next.jsはReactを内包する上位互換のフレームワークです。

React
UIを組み立てるための
「部品ライブラリ」

画面を「コンポーネント」という部品に分けて、propsとstateからHTML（見た目）を作ることだけに専念するライブラリです。

ルーティング、サーバーとの通信方法、ビルドの仕方などは決めていません。それらは自分で選んで用意する必要があります。

Next.js
Reactを内包した
「全部のせフレームワーク」

中身はそのままReactです。コンポーネント・props・stateの書き方は変わりません。

そのうえで、React単体には無かったルーティング・サーバー機能・画像最適化・ビルド設定などを標準搭載し、「Reactで画面を作る以外に必要なもの」を一式そろえています。

つまり

Next.js = React（部品を作る力）＋ルーティング・サーバー機能・最適化など（部品を届ける仕組み）

この2つ目の「届け方」の中でも、いちばん影響が大きいのが「HTMLをどこで・いつ組み立てるか（レンダリング方式）」の違いです。次のページからは、そこに絞って掘り下げます。

次のページでは、ReactとNext.jsの「結論」を先に一言でまとめます。

02

ReactとNext.jsの違い（レンダリング）

まず一番大事な結論だけ、先に押さえます。

この先の説明は、すべてこの1点の掘り下げです。

結論: 素のReactとNext.jsで「できること」が違う
素のReact（react-learning/）
CSRしかできない

Next.js

つまりNext.jsが足しているのは「新しい書き方」ではなく、「HTMLをいつ・どこで作るか」の選択肢です。

なぜReactは「ブラウザだけ」しか使えなかったの？

Reactはライブラリとして読み込まれているだけで、サーバー側のプログラムを書く仕組みがそもそもありません。

Next.jsはフレームワークとして「サーバー側で実行する場所（app/のフォルダ構成）」を用意しているため、同じReactのコンポーネントの書き方のまま、サーバー実行という選択肢が使えるようになります（01章で詳しく）。

次のページでは、そもそも「レンダリング」という作業自体を定義します。

前ページで「CSR/SSRの違い」と言いましたが、そもそもレンダリングという言葉自体を定義します。

レンダリングとは、コンポーネントの中身（JSXやstate）を、実際にブラウザが表示できるHTML/DOMに変換する作業です。

<RecipeCard recipe={r} />
// ただのJSオブジェクト

「どこでこの変換計算をするか」がCSR/SSR/SSG/ISRの違いになります。この計算は2つの全く違うコンピューターのどちらでも行えます。

ReactとNextのレンダリングの違いは？

レンダリング（＝HTMLへの変換）はブラウザとサーバーのどちらでも行えます。この「どこで」が両者の違いの正体です。

ブラウザ（クライアント）

ユーザー1人ぶんのマシンパワーを使う。
ネットワークが遅くても、一度JSが届けばその後は速く動ける。
ユーザーの手元にしかない情報（localStorageなど）に直接アクセスできる。

05

CSR — Client Side Rendering

ひとことで言うと: HTMLを組み立てる作業をブラウザの中でやる方式。

ReactはCSRしかできません。

▶ 具体的な処理の流れ — ユーザーがURLを開いてから
01
ブラウザが index.html をリクエストする
02
サーバーはほぼ空のHTML（<div id="root"></div>）とJSファイルのURLだけを返す — 画面はまだ真っ白
03
ブラウザがJSバンドル（Reactごと全部）をダウンロードし、パース・実行する
04
Reactが実行され、DOMを組み立ててここでやっと画面が表示される
05
以降のクリックや検索は、全部ブラウザ内のReactが処理する（サーバーへの依存なし）
具体例: 今のApp.jsx
// index.htmlの中身はこれだけ
<div id="root"></div>
<script src="/src/main.jsx"></script>

// main.jsx がブラウザで実行されて
// 初めてid="root"の中身が生まれる
ReactDOM.createRoot(
  document.getElementById("root")
).render(<App />);
向いている場面

ログイン後の管理画面・ダッシュボードなど「検索エンジンに拾われる必要がなく、開く人がログイン済みで限られる」画面。

向いていない場面

誰かに公開・共有するページ。初回表示の遅さとSEOの弱さが弱点になります（01章のQ&A参照）。
06

SSR — Server Side Rendering

ひとことで言うと: HTMLを組み立てる作業を、リクエストが来るたびにサーバー側でやる方式。

常に最新のデータでHTMLが作られます。

▶ 具体的な処理の流れ — ユーザーがURLを開いてから
01
ブラウザがURLをリクエスト
02
サーバーがその場でReactコンポーネントを実行し、DBやAPIからデータも取得してHTMLを組み立てる
03
完成済みHTMLが届き、この時点で内容が見える（JSはまだ届いていなくても文字や画像は表示済み）
04
裏でJSバンドルが届く
05
ハイドレーション（G5）が終わり、クリックや入力が効くようになる
具体例: Next.jsでの書き方
export default async function Page() {
  // cache:"no-store" = 毎回サーバーで
  // 新しく取得し直す → SSRになる
  const res = await fetch(
    "https://api/recipes/mine",
    { cache: "no-store" }
  );
  const myRecipes = await res.json();
  return <RecipeList recipes={myRecipes} />;
}
向いている場面

「ログインユーザーのマイレシピ」「在庫の残り数」など、アクセスするたびに中身が変わるページ。

コスト面の注意

アクセスのたびにサーバーが計算し直すため、SSG/ISRよりサーバー負荷が高く、表示もやや遅いのが弱点です。
07

SSG — Static Site Generation

ひとことで言うと: HTMLをデプロイする前に1回だけ作り置きしておく方式。

リクエスト時の計算がゼロなので、3方式の中で最速です。

▶ 具体的な処理の流れ
01
（デプロイ前） next build の実行時に、全レシピ分のHTMLを1つずつ生成しておく
02
作ったHTMLをCDNなどに配置してデプロイ完了
03
ユーザーがアクセス → 作り置きHTMLを即返すだけ（サーバーは何も計算しない、最速）
04
裏でJSが届き、ハイドレーションで操作可能に
05
レシピの中身を変えても、再ビルド・再デプロイするまで画面には反映されない
具体例: Next.jsでの書き方
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  // force-cache = ビルド時に1回だけ取得
  // してキャッシュを使い回す → SSG
  const { id } = await params;
  const res = await fetch(
    `https://api/recipes/${id}`,
    { cache: "force-cache" }
  );
  const recipe = await res.json();
  return <RecipeDetail recipe={recipe} />;
}
向いている場面

公開レシピの詳細ページのように、誰が見ても同じで、更新頻度が低いページ。

弱点

中身を更新するたびに再ビルドが必要。「新着レシピが増える一覧」のように更新はあるが都度SSRするほどではない場合は、次のISR（G4）が向いています。
08

ISR — Incremental Static Regeneration

ひとことで言うと: SSGの作り置きHTMLを、決めた時間ごとに裏側で作り直す方式。

SSGの速さと、SSRのような自動更新を両取りできます。

▶ 具体的な処理の流れ（例: 60秒ごとに再検証）
01
SSGと同じく、ビルド時（または初回アクセス時）に作り置きHTMLを用意
02
60秒以内のアクセスには、その作り置きHTMLを即返す（SSGと全く同じ速さ）
03
60秒を過ぎて誰かがアクセスすると、そのアクセスには古いHTMLを返しつつ、裏側で再生成を開始する
04
再生成が終わると、それ以降のアクセスから新しいHTMLに自動で切り替わる（再ビルド不要）

この「古いものを一旦返しつつ裏で更新する」考え方は stale-while-revalidate と呼ばれます。

具体例: Next.jsでの書き方
export default async function Page() {
  const res = await fetch(
    "https://api/recipes",
    // 60秒ごとに裏で再生成
    { next: { revalidate: 60 } }
  );
  const recipes = await res.json();
  return <RecipeList recipes={recipes} />;
}
向いている場面

「みんなのレシピ一覧」のように誰が見ても同じだが、新着が増えるページ。

SSR・SSGとの使い分け

「今すぐ確実に最新」が必須ならSSR、「多少の遅れは許容できる」ならISR、「ほぼ更新されない」ならSSG、が判断の目安です。

10

ハイドレーション（Hydration）

ひとことで言うと: サーバーが作った「見た目だけのHTML」に、ブラウザ側のReactが後からクリックやuseStateなどの「命」を吹き込む処理。

SSR・SSG・ISR、どの方式でも必ず1回発生します。

▶ 具体的な処理の流れ
01
サーバー製HTMLが届き、見た目だけは即座に表示される（この時点でボタンを押しても何も起きない）
02
裏でReact本体と各コンポーネントのJSがダウンロードされる
03
ReactがそのJSを実行し、「本来ならこういうDOMになるはず」という予想を組み立てる
04
予想と、実際に届いているサーバー製DOMを照合する
05
一致していれば、そのDOMにイベントリスナーとstateを紐付ける — ここでようやくクリックやuseStateが動き出す
⚠
一致していなければ → Hydration failed エラー
起きやすいミスの具体例
// サーバーでは実行時刻のA、ブラウザでは
// 数ミリ秒後の時刻Bになり、文字列が一致しない
<p>最終更新: {new Date().toLocaleTimeString()}</p>

// サーバーにはlocalStorageが存在しないので
// 常に「なし」判定 → ブラウザとズレる
<p>{localStorage.getItem("theme") ?? "デフォルト"}</p>
対処法

レンダリング中に「サーバーとブラウザで結果が変わりうる値」（現在時刻・乱数・localStorage・window幅など）を使わない。

どうしても必要なら、useEffect の中（＝ハイドレーション後、ブラウザ側だけ）で読み込みます。
11

ストリーミング / Suspense

ひとことで言うと: ページの中で遅いデータ取得がある部分だけを後回しにし、準備できた部分から先にHTMLを届ける仕組み。

「全部揃うまで真っ白」を防ぎます。

▶ 具体的な処理の流れ
01
レシピ詳細のうち「みんなの評価」だけ集計に時間がかかるとする。その部分を <Suspense> で囲む
02
サーバーは準備できたレシピ本体を先に送信開始（評価部分はまだ待たせない）
03
評価部分には一旦 fallback（スケルトンや「読み込み中」）が表示される
04
評価の集計が終わり次第、サーバーが追加でHTMLを送り、その部分だけ差し替わる（ページ全体の再読み込みなし）
具体例: Next.jsでの書き方
export default function RecipeDetailPage() {
  return (
    <article>
      <RecipeHeader />   ← 先に届く
      <Suspense fallback={<RatingSkeleton />}>
        <RatingSummary />  ← 遅れて届く
      </Suspense>
    </article>
  );
}
03章・06章との関係

フォルダに置く loading.tsx（06章）は、実はページ全体を自動でSuspenseで包む簡易版です。

ページの一部分だけを段階的に出したいときは、自分で <Suspense> を明示的に使います。
12

RSCペイロード — 遷移が速い裏側

ひとことで言うと: サーバーコンポーネントは、初回はHTMLとして届きますが、ページ内遷移のときは特殊な軽量データ形式（RSCペイロード）としてやり取りされます。

06章の <Link> がなぜ速いのか、の裏側です。

▶ 具体的な処理の流れ — 一覧ページから詳細ページへLinkで移動
01
<Link>が画面に見えた時点で、遷移先のRSCペイロードを先読み（prefetch）しておく
02
クリックすると、共通のlayout.tsx部分は再取得しない（すでに画面にあるものは使い回す）
03
先読み済みのRSCペイロード（差分だけの軽量データ）をReactが受け取り、ページ全体のHTMLではなく必要な部分だけを組み立て直す
04
画面が差し替わる — 通常のMPA遷移（JS版のdetail.html移動）のようなページ全体の再読み込みは起きない
なぜHTMLではなく専用データ形式を使うのか

HTML全体を毎回送ると、共通のヘッダーやレイアウトまで再送する無駄が出ます。

RSCペイロードは「サーバーコンポーネントの計算結果」を軽量なツリー構造で表現したもので、Reactはこれを受け取ってDOMのうち変わった部分だけを更新します。

普段のコーディングでこの形式を直接書くことはありませんが、「Linkが速いのはこの仕組みのおかげ」と知っておくと06章のprefetchが腹落ちします。

用語のおさらい

Q. なぜCSRのままではだめなの？
A. だめではありません。

ただしCSRは「最初に空のHTMLが届く」ため、①初回表示が遅い（JSを全部落として実行するまで真っ白）、②検索エンジンやSNSカードが中身を読めないことがある、という弱点があります。

レシピを他人に公開・共有するアプリでは、この2つが効いてきます。
02

セットアップ — Next.js導入コマンド（2026年7月時点）

05

"use client" が届く範囲

前ページで「対話が必要な部品だけに "use client" をつける」と書きましたが、その指示がどこまで効くのか、よくある誤解を含めて掘り下げます。

"use client" が届く範囲 — 誤解しやすいポイント

"use client" はそのファイル1つだけの印ではありません。

そのファイルがimportしている子コンポーネントすべても、まとめてクライアントバンドルに引き込まれます（これを「クライアント境界」と呼びます）。

✗ ありがちな失敗

今のApp.jsxを丸ごと持ってきて、先頭に "use client" を1行書いて終わりにする。

→ importされているSearchBox・RecipeList・RecipeCard・RegisterRecipeFormの全部品がクライアントに引き込まれ、SSRの利点（軽さ）が消える。
✓ 良い書き方

入力・対話のある末端の部品だけに "use client" を付ける。このアプリなら SearchBox・RegisterRecipeForm・RecipeCard（編集UI）の3つ。

→ 一覧の描画（RecipeList）やヘッダーはサーバーに残せ、引き込まれる範囲を最小化できる。
"use server" — 逆方向のもう1つの宣言
// app/actions.ts — Server Action
"use server";  // ← サーバーでだけ実行

export async function registerRecipe(formData) {
  // App.jsxのparseRecipeTextは純JSなので
  // サーバー側へそのまま移植できる
  const parsed = parseRecipeText(
    formData.get("recipeText"),
    formData.get("recipeUrl"));
  if (!parsed) return { error: "料理名の形式…" };
  await db.recipes.insert(parsed); // DB直操作OK
}

// RegisterRecipeFormから直接呼べる（API不要）
<form action={registerRecipe}>
  <textarea name="recipeText" />
  <button>レシピ追加</button>
</form>
"use client" とは向きが逆です。

"use client" は「ここから先はブラウザで動かして」というサーバー→クライアントの境界線。

"use server" は「この関数だけはブラウザから呼ばれてもサーバー側で実行して」というクライアント→サーバーの入口（＝Server Action）です。

07章の「Server Actions」はこの仕組みのことで、フォーム送信時にfetchやAPI Routeを自分で書く必要がなくなります。

06

データ取得 — useEffectの「後から取る」をやめる

レシピデータの読み書きの場面です。

今のApp.jsxは「useStateの初期値でlocalStorageから復元 → 変更のたびにuseEffectで保存」という形で、データの置き場はブラウザの中でした。

Next.jsではこの読み書きがサーバー側へ移り、コンポーネント自体をasyncにして、描画の前にawaitで取得します。

React — localStorage復元＋useEffect保存（今の実装）
// 今のApp.jsx: データ置き場はlocalStorage
// ① 初期値に関数を渡して復元（遅延初期化）
const [recipes, setRecipes] = useState(() => {
  const saved = localStorage.getItem("recipes");
  return saved
    ? JSON.parse(saved)
    : defaultRecipes;
});

// ② recipesが変わるたびにuseEffectで保存
useEffect(() => {
  localStorage.setItem(
    "recipes", JSON.stringify(recipes));
}, [recipes]);
⚙ この方式の限界
データはそのブラウザの中にしかないため、別の端末では見えず、他人と共有もできません。

さらにlocalStorageはサーバーに存在しないので、このコードはサーバーコンポーネントでは動かず、SSRしても空のHTMLしか作れません。
Next.js — サーバーで取得してから描画
// app/page.tsx（サーバーコンポーネント）
export default async function Page() {
  // 読み込み: 描画の前にサーバーで済ませる
  const recipes = await getRecipes();
  return <RecipeList recipes={recipes} />;
}

// 保存: useEffectではなくServer Action
"use server";
export async function saveRecipe(recipe) {
  await db.recipes.upsert(recipe);
  revalidatePath("/recipes"); // 一覧を更新
}
⚙ 何がどこに移るか
読み込みは await getRecipes()、保存はServer Actionへ。defaultRecipes.jsはDBの初期データ（seed）になります。

ブラウザにはデータ入りの完成HTMLが最初から届き、読み込み中表示は loading.tsx を置くだけです。
Q. じゃあuseEffectはもう使わない？
A. 出番は減りますが、なくなりません。

「初回のデータ取得」はサーバーコンポーネントに移りますが、ブラウザでしかできないこと（localStorage、タイマー、ブラウザAPIの購読など）はこれからも "use client" な部品の中でuseEffectを使います。

前作06章の知識はそのまま有効です。

app/api/recipes/route.ts（コピペで動く）
import { NextResponse } from "next/server";
import { getRecipes, addRecipe } from "@/lib/recipes";
import { parseRecipeText } from "@/lib/parseRecipeText";

// GET /api/recipes → 一覧取得
export async function GET() {
  const recipes = await getRecipes();
  return NextResponse.json(recipes);
}

// POST /api/recipes → 新規登録（handleRegister相当）
export async function POST(request: Request) {
  const { recipeText, recipeUrl } = await request.json();
  const trimmed = recipeText?.trim();
  if (!trimmed) {
    return NextResponse.json(
      { error: "レシピのテキストを入力してください。" },
      { status: 400 }
    );
  }
  const parsed = parseRecipeText(trimmed, recipeUrl);
  if (!parsed) {
    return NextResponse.json(
      { error: "料理名の形式が正しくありません。" },
      { status: 400 }
    );
  }
  const created = await addRecipe(parsed);
  return NextResponse.json(created, { status: 201 });
}

app/api/recipes/[id]/route.ts
import { NextResponse } from "next/server";
import { updateRecipe, deleteRecipe } from "@/lib/recipes";
import { parseRecipeText } from "@/lib/parseRecipeText";

// PATCH /api/recipes/1 → 編集保存（saveEdit相当）
export async function PATCH(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  const { editRecipeText } = await request.json();
  const parsed = parseRecipeText(editRecipeText?.trim() ?? "", "");
  if (!parsed) {
    return NextResponse.json(
      { error: "料理名の形式が正しくありません。" },
      { status: 400 }
    );
  }
  const updated = await updateRecipe(id, parsed);
  return NextResponse.json(updated);
}

// DELETE /api/recipes/1 → 削除（deleteRecipe相当）
export async function DELETE(
  _request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  await deleteRecipe(id);
  return NextResponse.json({ ok: true });
}

Prismaとは？ — 生SQLとの比較で理解する

Prismaは、TypeScript/JavaScriptからDBを操作するためのORM（Object-Relational Mapper）です。

schema.prismaというファイル1つにテーブル構造（モデル）を定義すると、そこから型安全なクライアント（Prisma Client）が自動生成され、SQL文を手で書かずにDB操作ができるようになります。

準備の流れ（スキーマを書いてからコードで使えるまで）
schema.prisma
データモデルを定義 → migrate dev
PostgreSQLにテーブルを作る → generate
TypeScript用のClientを生成 → コード
prisma.recipe.findMany()

migrateとgenerateは別の役割です。migrateはDBにテーブルを作る、generateはコードから呼べる型付きClientを作る、という違いを分けて覚えると混乱しません。

migrate devは成功すると内部でgenerateも自動実行してくれるため、通常は1コマンドで両方揃います。

アプリのコードからDBに届くまで
アプリのコード
prisma.recipe.findMany() → Prisma Client
schema.prismaから自動生成 → SQL文
SELECT * FROM "Recipe"... → PostgreSQL

Prisma = SQLを手書きする代わりに、TypeScriptの関数呼び出しでDB操作を表現できるようにする層。

実際に発行されるSQLはPrisma Clientが組み立てて実行するので、開発者が直接SQL文字列を書く必要がなくなります。

生SQL（pg などのドライバを直接使う場合）
// 型はついてこない。列名やテーブル名を
// タイポしても実行するまで気づけない
const result = await pool.query(
  'SELECT id, name, ingredients, steps, url ' +
  'FROM "Recipe" ORDER BY "createdAt" DESC'
);
const recipes = result.rows;
// recipes の型は any 相当
Prisma（ORM経由）
// schema.prismaのRecipeモデルから
// 戻り値の型が自動で決まる（補完も効く）
const recipes = await prisma.recipe.findMany({
  orderBy: { createdAt: "desc" },
});
// recipes: Recipe[]（name, ingredients... 全て型付き）

Q. SQLを覚えなくてもPrismaだけ使えればいい？
A. 基本のCRUD（findMany/create/update/delete）はPrismaの書き方だけで十分こなせます。

ただし複雑な集計や既存DBのトラブルシュートではSQLの知識が役立つ場面があるため、「SQLを完全に代替する」というより「日常的なDB操作を型安全に楽にする」道具と捉えるのが実態に近いです。

② prisma/schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model Recipe {
  id          Int      @id @default(autoincrement())
  name        String
  ingredients Json
  steps       String[]
  url         String?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}
③ .env
DATABASE_URL="postgresql://postgres:postgres@localhost:5432/recipe_app"
④ lib/db.ts（Prisma Clientのシングルトン）
import { PrismaClient } from "@prisma/client";

const globalForPrisma = global as unknown as { prisma: PrismaClient };

export const prisma =
  globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = prisma;
}

ECS Fargateタスク定義で気にする点

・コンテナのポートは3000（上のDockerfileのEXPOSEに合わせる）
・DATABASE_URL はSecrets Manager／SSM Parameter Storeから注入し、タスク定義に平文で書かない
・PostgresはローカルのDocker Composeとは別に、本番はAmazon RDS for PostgreSQLを使うのが基本形（ECS Fargateのコンテナは"ステートレス"に保つ）
・ALBのヘルスチェックパスは / かAPI用の軽量なRoute Handler（例: /api/health）を用意する
・ログはawslogsドライバでCloudWatch Logsへ
